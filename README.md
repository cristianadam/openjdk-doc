Information
-----------

This package builds an offline Qt Help archive (.qch) of the Java SE
documentation -- the API reference published at
<https://docs.oracle.com/en/java/javase/25/docs/api/>, together with the
specifications and the manual pages for the JDK tools that are released
alongside it.

It is the Java counterpart of
[cppreference-doc](https://github.com/p12tic/cppreference-doc), and follows
the same idea: take the documentation as it is published, fit it to a help
viewer, and hand the result to `qhelpgenerator`.  The archive is read by Qt
Assistant and by the help pane of Qt Creator, and by anything else that
opens a .qch.

The documentation itself is not in this package and is far too large to be.
Oracle publishes the whole of it as one zip -- about 55 MB, 11,000 pages --
and serves it from a plain URL with no login, so there is no crawling to do:

    make source

reads the download page for the release named by `JDK_VERSION`, fetches the
archive it links and unpacks it into `reference/`.  Then

    make doc_qch

builds `output/openjdk-doc-en-java25.qch`.  [Building
it](#building-it) has the whole of it, Python environment and all.

The archive it builds is Oracle's documentation, and Oracle says what may be
done with it: read it, keep it off the Internet unless you have asked and
been given permission.  See [Redistribution](#redistribution) before passing
one on.

Another feature release is a variable away, for as long as Oracle keeps a
download page for it:

    make source JDK_VERSION=21
    make doc_qch JDK_VERSION=21

What this is built and tested against is JDK 25.  An older release is worth
trying -- the download page, the bundle and the lists javadoc leaves beside
the pages are all the same shape, and where the stylesheet sits is looked
for rather than assumed -- but javadoc only moved its colors into CSS custom
properties around JDK 21, and the dark sheet is derived from those, so a
bundle older than that will come out with a dark background and light
pages.

Dependencies
------------

`python3`, `lxml` and `qhelpgenerator`.  `lxml` is the only third-party
Python package the build needs; `flake8`, in `requirements-ci.txt`, is for
`make check` alone.

`qhelpgenerator` ships with Qt, which keeps it under `libexec` -- so it is
never on `PATH` and the build has to be told where it is:

    /usr/lib/qt6/libexec/qhelpgenerator                  Debian, Ubuntu
    $(brew --prefix qt)/share/qt/libexec/qhelpgenerator  Homebrew
    ~/Qt/<version>/<platform>/libexec/qhelpgenerator     the Qt installer

On Debian and Ubuntu it is in the `qt6-documentation-tools` package.

Building it
-----------

Where `lxml` is packaged, as it is on Debian and Ubuntu, there is nothing to
set up:

    sudo apt install python3-lxml qt6-documentation-tools
    make source
    make doc_qch qhelpgenerator=/usr/lib/qt6/libexec/qhelpgenerator

Anywhere else -- macOS, or a Python that has no `lxml` -- a virtual
environment is the shortest way there, and `python=` points the build at it:

    python3 -m venv venv
    ./venv/bin/pip install -r requirements.txt

    make source python=./venv/bin/python
    make doc_qch python=./venv/bin/python \
         qhelpgenerator=$(brew --prefix qt)/share/qt/libexec/qhelpgenerator

`make source` downloads and unpacks the bundle, which is 55 MB over the wire
and about 330 MB on disk; `make doc_qch` writes the .qch, which is about
50 MB.  Neither takes long -- on a 2024 laptop the download is a few seconds
and the build under ten, most of it rewriting the eleven thousand pages
across every core there is.

Both variables have to be given **on the command line**.  Exporting them
does nothing: a definition in a makefile beats one from the environment
unless make is run with `-e`.  If repeating them palls, change the two
defaults at the top of the Makefile.

`make source` is the only target that needs the network.  Once the bundle is
there, `make clean` removes what was built from it and leaves it alone, so
the archive can be rebuilt as often as you like; `make distclean` throws the
bundle away as well.

`make check` runs flake8 and the unit tests.  Those need neither the network
nor the bundle -- they work on fixtures -- so they are worth running before
anything is downloaded:

    ./venv/bin/pip install -r requirements-ci.txt
    make check python=./venv/bin/python

Using it
--------

Qt Creator takes the archive under *Preferences > Help > Documentation >
Add*, and Qt Assistant under *Preferences > Documentation > Add*, or from a
terminal:

    assistant -register output/openjdk-doc-en-java25.qch

`make install` puts it under `/usr/share/openjdk-doc/doc/qch`; `prefix` and
`DESTDIR` move that where you need it.

What the build does
-------------------

The pages are generated by javadoc and are laid out for a browser.  The help
viewers that read the archive render with litehtml, which follows a
stylesheet and a box model much as a browser does but runs no JavaScript and
lays out no CSS grid.  Three things follow, and they are most of what the
build is.

 1) **The summary tables are rebuilt.**  Every list of fields, constructors
 and methods on a class page is a flat run of `<div>`s placed by
 `grid-template-columns`, and read without grid that is one cell per line.
 `commands/qch_html.py` folds each run back into the `<table>` it stands for
 -- the column count is in the class name -- which litehtml lays out as the
 page means it.  There are 29,000 of them in a JDK 25 bundle.

 2) **The scripted furniture goes.**  The search box, the filter over the
 contents of a page, the buttons that switch a method table between "static"
 and "instance", the sidebar table of contents: each needs a script, and
 each is something the help viewer provides anyway, out of its own Contents
 and Index panes.  The breadcrumb is kept and moved to the top of the
 content.

 3) **The stylesheet is resolved and a dark one is derived.**  javadoc
 declares every color, font and font size it uses as a CSS custom property,
 fifty-six of them in one `:root` block.  `commands/qch_css.py` reads the
 sheet once and writes it out twice with the variables resolved -- against
 javadoc's palette for the light sheet and against `qch-dark.css` for the
 dark one.  Asked for `offline-simple.css`, Qt Assistant and Qt Creator both
 serve `offline-dark.css` in its place when their own theme is dark, so the
 pages follow the theme of the viewer without the archive having to say
 anything.  The fonts and the type scale are set in `qch-viewer.css`, which
 is where to go to change how the pages read.

The contents and the index are not parsed out of the pages: javadoc writes
the lists its own search box works from -- every module, package, type and
member it documented -- and `commands/javadoc_index.py` reads those.  The
Contents pane gets the shape of the API, module by module and package by
package, stopping at the types; the Index pane gets all of it, 63,000
keywords, each type under both its simple and its qualified name and each
member under the type it belongs to.

What is left out of the archive is the A-Z index, which is 24 MB of pages
saying what the Index pane says in a better form, and the search page, which
without a script is an empty form.

Layout
------

    fetch_docs.py          downloads the bundle Oracle publishes
    preprocess_qch.py      rewrites every page, and writes the stylesheets
    build_qhp.py           writes the help project
    commands/qch_html.py   one page, rewritten
    commands/qch_css.py    the light and dark stylesheets
    commands/javadoc_index.py  the lists javadoc leaves beside the pages
    commands/qhp.py        the contents, the index and the file list
    qch-viewer.css         the fonts and the fit to a help pane -- edit this
    qch-dark.css           the dark palette -- and this

Redistribution
--------------

**Build the archive; do not publish it.**  This package is a converter, and
it is deliberately only a converter: no page of Oracle's documentation is in
this repository, and `make source` fetches the bundle from Oracle onto the
machine that is going to read it.  What comes out of `make doc_qch` is a
rearrangement of the copy you just downloaded, and it is Oracle's to say
what may be done with it.

What Oracle says, in its [Documentation Redistribution
Policy](https://www.oracle.com/java/technologies/redistribution-policy.html),
is worth reading before putting a .qch anywhere:

> The Java SE API Specification is not redistributable.

> API specifications can be redistributed internally without special
> permission.  They cannot be made available on the Internet.

> **Redistribution of Popular Formats** - Limited permission has been
> granted to a few individuals to redistribute documentation in formats we
> wouldn't otherwise support, such as WinHelp and HTMLHelp (permission given
> to Franck Allimant) and Macintosh 31-character-filename format (permission
> given to Stephen Revilak).  These requests are handled on a case-by-case
> basis

A Qt Help archive is precisely one of those formats Oracle "wouldn't
otherwise support", so this package stands exactly where the CHM files
Franck Allimant has published since the Sun days stand -- Kyle Cordes
[wrote about those in 2007](https://kylecordes.com/2007/java-win-help), and
suspected "it was unauthorized at first, but some kind of peace was made
with Sun, which now links to the site".  Peace made on a case-by-case basis
for one person is not permission for anybody else, so:

 * Building the archive and reading it yourself is what it is for.
 * Putting it on an internal server for your colleagues is what the policy
   calls internal redistribution, which it allows without asking.
 * Putting it on the Internet -- a release asset, a package repository, a
   file on a website -- is what the policy says not to do, and is the thing
   for which permission has to be asked and granted first.  Ask Oracle, and
   if they grant it, attribute their copyright and trademarks as the
   Attribution section of the policy asks.

For that reason the workflow in `.github/workflows/qch.yml` builds the
archive and checks it on every push, but uploads nothing unless the
repository variable `PUBLISH_QCH` is set to `true`.  Turn it on only if you
have the permission that makes it lawful for you.

Linking needs no permission at all, which is what the online documentation
at <https://docs.oracle.com/en/java/javase/25/docs/api/> is for.
